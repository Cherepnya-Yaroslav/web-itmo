    Лабораторная работа 3. Docker, parser-service и очереди

    Тема и цель

    ЛР3 объединяет приложение из ЛР1 и парсер из ЛР2 в единый Docker Compose-стек. Дополнительно реализованы два способа запуска парсинга:

    1. синхронный HTTP-вызов отдельного parser-service;
    2. фоновая постановка задачи в Redis/Celery с последующей проверкой результата.

    Состав проекта

    Файл Назначение
    lab3/docker-compose.yml пять сервисов, сеть, порты, volume и healthcheck
    lab3/Dockerfile.app образ основного FastAPI-приложения и Celery worker
    lab3/Dockerfile.parser образ отдельного parser-service
    lab3/parser_service/main.py FastAPI-сервис с endpoint /parse
    lab1/app/services/parser_client.py HTTP-клиент основного приложения
    lab1/app/routers/parser.py HTTP- и Celery-endpoint основного API
    lab1/app/workers/celery_app.py конфигурация Celery
    lab1/app/workers/tasks.py фоновая задача parser.parse_url
    lab2/parser_common.py общий парсер и сохранение в PostgreSQL

    Архитектура контейнеров

    app:8000
  ├── HTTP -> parser:8001 -> PostgreSQL
  └── Redis broker -> celery_worker -> parser_common -> PostgreSQL

db:5432 inside network, 5433 on host
redis:6379 inside network and on host
    Сервис Назначение Публикуемый порт
    app API ЛР1 и endpoint запуска парсера 8000
    parser отдельный HTTP parser-service 8001
    db PostgreSQL 5433:5432
    redis broker и result backend Celery 6379
    celery_worker обработка фоновых задач внутренний

    Для db и redis настроены healthcheck. app ждёт готовности базы, Redis и parser-service. PostgreSQL использует volume postgres_data, поэтому данные сохраняются после обычного docker compose down.

    Dockerfile.app

    Dockerfile.app использует python:3.12-slim, копирует lab1 и lab2 в /workspace, устанавливает пакет ЛР1 и зависимости ЛР2, задаёт PYTHONPATH=/workspace/lab1:/workspace/lab2 и создаёт пользователя appuser.

    Этот образ используется дважды:

    • сервис app запускает alembic upgrade head, затем uvicorn app.main:app;
    • сервис celery_worker запускает celery -A app.workers.celery_app.celery_app worker --loglevel=info.

    Dockerfile.parser

    Dockerfile.parser также использует python:3.12-slim, копирует lab2 и lab3/parser_service, устанавливает FastAPI, Uvicorn и зависимости парсера, а затем запускает:

    uvicorn main:app --host 0.0.0.0 --port 8001

    Parser-service запускается от пользователя appuser и получает адрес БД через DATABASE_URL.

    parser-service

    Файл lab3/parser_service/main.py создаёт отдельное FastAPI-приложение Parser Service.

    Модели:

    • ParseRequest принимает URL типа HttpUrl;
    • ParseResponse возвращает URL, title, status, error, worker_type и duration_ms.

    Endpoint:

    GET  /health
POST /parse

    Внутри parse_url() блокирующий parse_and_save_url() запускается через asyncio.to_thread(), чтобы не блокировать event loop parser-service.

    HTTP-вызов из основного API

    Основной роутер находится в lab1/app/routers/parser.py, клиент - в lab1/app/services/parser_client.py.

    Endpoint:

    POST /api/v1/parser/parse

    Пример:

    curl -X POST http://localhost:8000/api/v1/parser/parse \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://example.com"}'

    Путь запроса:

    client -> app:8000 -> parser:8001 -> parser_common -> PostgreSQL

    Основное приложение ждёт ответ parser-service и возвращает его клиенту. При ошибке HTTP-клиент поднимает 502 Bad Gateway с понятным описанием проблемы.

    Celery и Redis

    lab1/app/workers/celery_app.py создаёт Celery-приложение с broker redis://redis:6379/0 и backend redis://redis:6379/1.

    lab1/app/workers/tasks.py объявляет задачу parser.parse_url. Она получает URL, вызывает parse_and_save_url(url, worker_type="celery") и возвращает сериализованный результат.

    Endpoint постановки:

    POST /api/v1/parser/tasks

    Endpoint проверки:

    GET /api/v1/parser/tasks/{task_id}

    Путь фоновой задачи:

    client -> app -> Redis broker -> celery_worker -> PostgreSQL
                                      └-> Redis result backend

    Запуск

    cd lab3
docker compose up --build

    Для фонового запуска в отдельном терминале:

    TASK_ID=$(curl -s -X POST http://localhost:8000/api/v1/parser/tasks \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://example.com"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["task_id"])')

curl http://localhost:8000/api/v1/parser/tasks/$TASK_ID

    Сначала возможен статус PENDING, после обработки ожидается SUCCESS и объект result с title страницы.

    Прямой вызов parser-service:

    curl -X POST http://localhost:8001/parse \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://example.com"}'

    Проверка требований

    Требование Статус
    FastAPI упакован в Docker выполнено
    PostgreSQL работает в Docker выполнено
    Парсер из ЛР2 подключён выполнено
    Есть Dockerfile приложения выполнено
    Есть Dockerfile parser-service выполнено
    Есть Docker Compose выполнено
    Есть HTTP-вызов парсера выполнено
    Есть Redis выполнено
    Есть Celery worker выполнено
    Результат сохраняется в PostgreSQL выполнено

    Фактический результат

    Стек был собран и запущен. Контейнеры app, parser, celery_worker находятся в состоянии Up, db и redis - healthy. Оба /health endpoint вернули {"status":"ok"}. Синхронный HTTP endpoint вернул Example Domain, а фоновая Celery-задача завершилась со статусом SUCCESS и вернула тот же заголовок.

    Где открыть результат

    • Swagger основного API: http://localhost:8000/docs
    • Swagger parser-service: http://localhost:8001/docs
    • Health основного API: http://localhost:8000/health
    • Health parser-service: http://localhost:8001/health

    Периодический запуск через Celery Beat в текущей реализации не добавлялся: обязательная часть работы - ручная постановка задач через HTTP API.
